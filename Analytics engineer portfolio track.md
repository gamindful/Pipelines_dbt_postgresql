# Analytics Engineer Portfolio Track

Five financial-data projects that between them exercise all seven domains of the
**dbt Analytics Engineering Certification**, built on the `analytics_lab`
database. Each ends in something showable — not an exercise to delete.

## Where everything lives

One database, one schema per domain. See [database.md](database.md) for how it
was built and [README.md](README.md) for the architecture.

```
analytics_lab
├─ credit_risk        Project 1 sources      sql/03_credit_risk_schema.sql
├─ bank_marketing     Project 2 sources      sql/04_bank_marketing_schema.sql
├─ bankruptcy         Project 3 sources      sql/05_bankruptcy_schema.sql
├─ market_data        Project 4 sources      sql/06_market_data_schema.sql
├─ staging            dbt-owned · views
├─ intermediate       dbt-owned · ephemeral
└─ marts              dbt-owned · tables
```

**The loader owns the source schemas; dbt owns the other three.** A bad
`dbt run` can never destroy ingested data.

### Getting data in

On the **server**, once per schema:

```powershell
psql -U postgres -d analytics_lab -f server_side\sql\04_bank_marketing_schema.sql
```

Then, for any UCI dataset:

```powershell
python server_side\utils\download_uci.py --dataset bank_marketing
python server_side\utils\load_uci.py     --dataset bank_marketing
```

`--list` on either script shows every dataset and where it lands. Project 4's
market data uses the existing `download_dataset.py` / `load_dataset.py` pair
instead, since it comes from yfinance rather than UCI.

On the **client**, nothing else is needed — one database means no `--profile`
and no `--target`:

```bash
dbt build --select credit_risk_marts
```

## 1 · Credit Risk Marts

**Schema** `credit_risk` · **Sources** `credit_default` (30,000), `german_credit` (1,000)
**Covers** materializations · DRY · generic + singular tests · docs · grants

Two credit datasets with genuinely different shapes force a real staging layer
instead of `select *`.

- Replace raw passthrough with explicit casts, generated by `codegen` then hand-corrected.
- Build `int_` models for credit-utilisation and payment-history logic used by more than one mart.
- Write one singular test a business person would recognise — no client has a negative credit limit.
- Add a custom generic test taking a `column_name` argument so it applies to both datasets.
- Turn on the `grants` config for marts; confirm a reader role can select but not write.

### Data quality already found in `credit_default`

Profiled before modelling. The raw table keeps these faithfully; staging fixes them:

- `education` is documented 1–4 but also contains **0, 5, 6** (345 rows)
- `marriage` is documented 1–3 but also contains **0** (54 rows)
- Their default rates are wildly inconsistent (0.00%, 5.69%, 6.43%) against 19–25% for documented codes — collapse to one `other` category
- Target is imbalanced: **22.1%** default
- Negative `bill_amt*` values are legitimate overpaid balances — do not "fix" them

A `not_null` test catches none of this. An `accepted_values` test on the decoded
staging column catches all of it.

**Ships as** a documented DAG with green tests, browsable via `dbt docs serve`.

## 2 · Campaign Funnel, Incrementally

**Schema** `bank_marketing` · **Source** `campaign_contacts` (~45,000)
**Covers** incremental strategies · snapshots · state selection · `dbt retry` · `--empty`

Large enough that full refreshes get annoying — which is the point.

- Load in two passes so the incremental branch runs on real new rows, not a synthetic `where 1=0`.
- Implement the same model with `append`, `delete+insert` and `merge`; time each and write down which you would defend in review.
- Add a YAML snapshot tracking campaign outcome changes over time.
- Validate logic without touching data using `dbt run --empty`; practise `dbt retry` after a deliberate failure.
- Save a production `manifest.json` and run `--select state:modified+` against it.

> **`duration` leaks the target.** It is the call length in seconds, known only
> *after* the call ends — so a model using it scores brilliantly and is
> worthless. Excluding it, and documenting why, is the analytical judgement this
> dataset is really testing.

**Ships as** a written comparison of the three incremental strategies with real timings.

## 3 · Bankruptcy Signals Under Contract

**Schema** `bankruptcy` · **Sources** `polish_bankruptcy`, `taiwanese_bankruptcy`
**Covers** contracts · constraints · model versions · deprecation · `dbt_expectations`

Two markets, ~160 financial ratios between them, no shared column naming.
Governance stops feeling bureaucratic the moment a consumer depends on a shape
you might change.

- Put `contract: enforced` on the shared mart; watch a deliberate type change fail at build time rather than in production.
- Declare `not_null` and `primary_key` constraints in YAML. Note which Postgres enforces versus which dbt only asserts.
- Ship `v1`, then `v2` with a renamed column, keeping both live and marking `v1` deprecated.
- Use `dbt_expectations` for distribution checks a plain `not_null` would miss.

> These two tables are loaded with the **inferred** strategy — created from the
> file's own header rather than hand-written DDL, because nobody has read 160
> ratio names and typing them is how silent mismatches happen. Generate the
> staging models with `codegen` for the same reason.

**Ships as** a versioned, contracted mart plus a migration note for the imaginary consumer of `v1`.

## 4 · Market Data & External Dependencies

**Schema** `market_data` · **Sources** `assets`, `price_history` (yfinance)
**Covers** source freshness · exposures · microbatch · packages

The only source in the portfolio that actually changes, which is what makes
freshness and time-partitioned incrementals meaningful rather than theoretical.

- Refresh with `download_dataset.py`, then `load_dataset.py` — it upserts, so re-runs are safe.
- Set `warn_after` / `error_after` against `loaded_at` and let one deliberately go stale.
- Build a `microbatch` incremental model partitioned by `trade_date`; reprocess a single window without a full refresh.
- Declare an `exposure` for a notebook or dashboard so the DAG shows who breaks if a model changes.
- Optional: add Numerai or DrivenData as a gated source. **Never commit their data** — both forbid redistribution.

**Ships as** a freshness-monitored pipeline whose lineage reaches past dbt into a named consumer.

## 5 · Operating the Pipeline

**Sources** everything already built
**Covers** `dbt clone` · deferral · DAG failure points · behaviour flags · compiled code

No new datasets. The capstone that turns four projects into one system, mapping
to the two domains people most often fail.

- Add a `prod` target, then use `dbt clone` to stand up a dev environment without recomputing anything.
- Run with `--defer` against the prod manifest so unbuilt models resolve upstream instead of failing.
- Break a model on purpose mid-DAG; read the failure back to a root cause from `target/compiled/`.
- Write the whole thing up as the repository README — what it does, how to run it, what you would change next.

**Ships as** a repo someone else could clone and run against their own Postgres in under ten minutes.

## Data sources

The distinction that matters for a public portfolio is not quality — it is
whether you may commit the bytes.

| Source | Access | Commit data? |
|---|---|---|
| **UCI ML Repository** — all of Projects 1–3 | open | Yes — CC BY 4.0 |
| **Hugging Face** — financial sentiment, filings | open | Check each dataset card |
| **yfinance** — Project 4 market data | open | Yes, small extracts |
| **Numerai** | account | **No** — terms forbid redistribution |
| **DrivenData** | account | **No** — per-competition terms |
| **DataSource.ai**, **CodaLab** | account | **No** |
| **Google Dataset Search** | open | An index, not a host |

> Prefer committing the **recipe** over the bytes even where licensing allows
> it. GitHub rejects files over 100 MB, and a repo full of CSVs is the clearest
> signal to a reviewer that no pipeline exists. `download_uci.py` plus
> `load_uci.py` reproduce every dataset from scratch.

## Conventions worth keeping

**Staging does exactly four things:** cast, rename, light cleanup, nothing else.
No joins, no aggregation — those belong downstream. Name them
`stg_<source>__<entity>.sql`.

**Generate column lists, never type them.** After loading:

```bash
dbt run-operation generate_source --args '{"schema_name":"credit_risk","database":"analytics_lab"}'
dbt run-operation generate_base_model --args '{"source_name":"credit_risk","table_name":"credit_default"}'
```

**Packages worth adding to `packages.yml`:**

```yaml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.3.0", "<2.0.0"]
  - package: dbt-labs/codegen
    version: [">=0.13.0", "<0.15.0"]
  - package: metaplane/dbt_expectations
    version: [">=0.10.0", "<0.11.0"]
```

**Every raw table carries `loaded_at TIMESTAMPTZ NOT NULL DEFAULT now()`.**
Without it `dbt source freshness` cannot be configured at all, and Project 4
depends on it.

**Never end a model with `limit`.** dbt appends its own, producing
`syntax error at or near "limit"`. Use `--limit N` on the command line instead.
